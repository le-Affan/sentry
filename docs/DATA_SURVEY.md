## 3. Gap analysis

Blunt version: **VCDB supplies the incident's *meaning*. It supplies almost none of the
incident's *telemetry*.** Measured against the input spec in `docs/SCOPE.md` §2, the
majority of a telemetry blob — including nearly every EVENTS row — has to be
synthesized by our templating code.

### 3.1 What VCDB can actually supply

Real, per-record, straight out of a VERIS document:

- **Victim context.** `victim.industry` (NAICS, 100% present), `victim.employee_count`
  (72.8% informative), country/state. This is genuinely the organization that was
  breached, and it maps cleanly onto the metadata block.
- **Incident date.** 43.4% of records have year+month+day. That is a real date.
- **What kind of thing happened.** `action.*.variety` across 117 distinct values — real
  labels for phishing, ransomware, stolen creds, exploit-vuln, and so on.
- **What kind of asset was involved.** `asset.assets.variety` across 88 values, though
  as a *category* (`S - Database`, `U - Desktop or laptop`), never a named machine.
- **Whether data was disclosed and roughly how much.** `attribute.confidentiality.*`,
  including `data_disclosure` and `data_total`. This is what makes severity derivable.
- **A human-written narrative.** 95.1% of records have a `summary`, median 24 words.

### 3.2 What VCDB cannot supply

The telemetry-detail scan in §1.5 is the answer, and it is close to a flat no. Across
all 10,596 records and every string field in each:

| Primitive the input spec requires | Found in VCDB |
|---|---|
| IPv4 addresses | 4 records (0.04%) |
| SIEM-style hostnames | 3 records (0.03%) |
| Event-level ISO timestamps | 1 record (0.01%) |
| Windows file paths | **0 records** |
| Process names | 25 records (0.24%) |
| File hashes | 6 records (0.06%) |
| Ports | 1 record (0.01%) |

The handful of hits are incidental mentions inside free-text `summary` and `notes`
fields — `1.1.1.1` as a placeholder, `/etc/shadow` named in a narrative — not
structured fields we could ever template from. The `domain_name` pattern looks like a
6.5% hit rate, but inspection shows it is matching news-source URLs
(`krebsonsecurity.com`) and organization names in `victim.victim_id`, not asset
hostnames. Treat it as zero.

There is also **no event log of any kind**. VERIS records one incident as a set of
classification facets, not as a sequence of observations. There is no field that
contains, or could be decomposed into, an ordered list of things that happened. The
closest thing is `timeline.{compromise,exfiltration,discovery,containment}.unit`, which
gives a coarse duration bucket (`Minutes`, `Days`, `Months`) for 11–26% of records.
That constrains *how far apart* synthesized events should be spaced. It does not tell
us what the events were.

**So: essentially 100% of EVENTS rows must be invented.** Their number, order,
timestamps, IPs, hostnames, event types, and descriptions are all our templating code's
output. VCDB constrains the *shape* of the invented sequence — a `social.Phishing` +
`malware.Ransomware` record should yield a phishing-then-encryption chain — but every
individual row is synthetic. The same is true of every hostname, every IP, every
account name, every file path, and every hash in the blob.

### 3.3 The ground-truth label problem

This is the more serious finding, and it was not visible before pulling the data.

The `vz-risk/veris` repo ships an official VERIS → ATT&CK crosswalk, which looked like
the obvious source of ground-truth technique IDs. **It cannot serve that purpose.**
Every substantive row carries `mapping_type = related-to`; `score_category` is empty on
all 1,270 rows. There is no "primary technique" designation. The result:

- 178 VERIS enum paths are mapped, to 589 distinct ATT&CK IDs.
- Only 64 of those 178 map one-to-one. Median fan-out is 2; the worst,
  `action.hacking.variety.Abuse of functionality`, maps to **115** techniques.
- Applied to records: 4,270 VCDB records (40.3%) have at least one mappable action, but
  only **15** resolve to exactly one candidate technique. 3,920 resolve to six or more.
- Of those 15, only 5 have a summary of 25+ words.

Fifteen usable records against a target of ~1,000 pairs. The crosswalk is dead as an
automatic labeller.

**Consequence for the project:** the ground-truth technique ID in `## Attack Technique`
must come from a hand-curated lookup — one canonical ATT&CK technique chosen per VERIS
action variety — not from the shipped crosswalk. This is feasible: 4,364 records
(41.2%) carry a `hacking`, `malware`, or `social` action, and the distribution is
concentrated, so curating the top ~15 varieties (`malware.Ransomware`,
`hacking.Exploit vuln`, `social.Phishing`, `hacking.Use of stolen creds`, …) covers the
bulk of that pool. That is roughly a 15-row table to write by hand in the dataset-build
phase, and it should be written down and version-controlled as a project artifact,
because it is a labelling decision, not an implementation detail.

The remaining ~60% of VCDB — `error.Misdelivery`, `physical.Theft`,
`misuse.Privilege abuse` — has no ATT&CK equivalent and should be excluded rather than
force-mapped. ATT&CK models adversary intrusion behaviour; a lost laptop is not a
technique.

### 3.4 ATT&CK

No gaps. 697 active techniques, 100% with a well-formed ID, name, and non-empty
description; median description 163 words. It is directly usable as a retrieval corpus
once STIX citation markers are stripped and long descriptions are truncated to fit the
1024-token budget.

### 3.5 Honest summary of what this dataset is

The training pairs will be **synthetic telemetry generated from real incident
classifications, paired with reports derived from those same classifications.** That is
a legitimate and defensible construction for this project, and it is what the ~900/100
split will consist of — but it must be stated plainly rather than described as "training
on real security telemetry," which it is not. Three consequences to carry forward:

1. **Grounding score measures template consistency, not real-world faithfulness.** The
   entities the model is scored against are ones we invented. The metric still catches
   hallucination, which is what it is for, but it does not validate against reality.
2. **Technique-ID accuracy is bounded by the hand-curated lookup.** The model can only
   be as right as our variety→technique table. Errors in that table become systematic
   errors in the ceiling, invisible to the metric.
3. **The model may learn our templating grammar rather than incident analysis.** If
   every phishing blob is generated from the same skeleton, a model can score well by
   pattern-matching the template. Varying skeletons per action variety, and reserving a
   few hand-written blobs for the test split, is the mitigation — decide this in the
   dataset-build phase, before generating 1,000 pairs.
